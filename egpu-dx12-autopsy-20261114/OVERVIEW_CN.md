## 一、问题起点与最初的完美假说

Zero 家里先后买过 3 个外置显卡坞（1 个 OCuLink + 2 个 USB4），长期遇到一个极其典型的反常痛点：
1. 在 OCuLink 外接 `RTX 5090`（HDMI 直插外置卡，排除内屏回传）上玩国产虚幻 5 大作（《影之刃零》、《黑神话：悟空》），即使开到 **4K DLSS 性能档（内部 1080p）**，帧率依然很低（复杂大场景掉到 **30–40 FPS**），此时 **GPU 占用率只有 ~50% 在闲等**；而在直插 PCIe x16 的台式机上完全无此问题；
2. 换到带宽更窄、延迟更高的 **USB4 显卡坞** 上更加严重，连 RE 引擎的《生化危机 9》都会卡顿。

前一晚我们对《影之刃零》（`PBZ.exe`）做静态反汇编，在偏移 `0x306F543–0x306F7C4` 抓到其三大动态上传分配器（`Small Block`、`Big Block`、`Fast Constant Page`）全部硬编码为 **`D3D12_HEAP_TYPE_UPLOAD = 2`（驻留主机系统内存）**，全程序无 `D3D12_HEAP_TYPE_GPU_UPLOAD = 5`（ReBAR 显存直写堆）分支。据此提出初始假说：**怀疑游戏把每帧几十 MB 动态缓冲放在系统内存 `UPLOAD` 堆被 GPU 跨 Pass 反复隔空倒吸，吸爆了 OCuLink 总线，只要写一个 `dxgi.dll` 把 `UPLOAD (2)` 透明偷梁换柱为 `GPU_UPLOAD (5)` 就能一举破局。**

## 二、四轮真机实弹实验：微基准大胜，真游戏当场证伪！

深夜远程连回北京客厅 `rtx5090` 真机，编写 `d3d12_egpu_probe.exe` 与 `dxgi.dll`（`v0.1` → `v0.3.1`）连打四仗，跑出了教科书级的对照结果：

### 1. Phase 1 & 2：合成微基准大获全胜（GPU 阶段快 **288 倍**）
- 实测 OCuLink 5090 开启了 `GPUUploadHeapSupported = 1`（注：但 `nvidia-smi -q` 显示空闲物理 BAR1 仅 `28 MiB`，分配 `<=16 MiB` 首次写入满速 `5.4 GB/s`，分配 `>=24~256 MiB` 时首次映射写入耗时陡增至 `19~208 ms`，存在 WDDM 滑窗重映射开销）；单次 `64B Copy -> READBACK -> Fence Event` 跨桥往返中位数为 **`85–126 µs`**。
- 对 `32 MiB × 8 Pass` 重复读取微基准，一字不改探针 EXE、仅靠同目录放入 `dxgi.dll (mode=1)` 自动将 `UPLOAD` 提拔为 `GPU_UPLOAD`：
  - **`mode=0`（原版 `UPLOAD=2` 跨桥倒吸）**：GPU 中位耗时 **`44.168 ms`**（端到端 `48.873 ms`，约 `6.08 GB/s` 顶死 PCIe Gen4 ×4 有效带宽上限）；
  - **`mode=1`（透明提拔 `GPU_UPLOAD=5`）**：GPU 中位耗时暴降至 **`0.153 ms`**（**提速 288 倍**！端到端降至 `6.460 ms`）。

### 2. Phase 3：《影之刃零》真机实测——当场证伪「`UPLOAD` 吸爆带宽论」！
清理旧第三方补丁、关闭 60Hz VSync 后，在同一关卡存档点（4K + 光追全开）实测 60 秒（4,000+ 帧）：

| 配置档位 | 实测 FPS | 帧时中位 / P99 | PCIe `RX` (Host→GPU) | PCIe `TX` (GPU→Host) | GPU SM 利用率 | 普通 `UPLOAD` 根绑定 |
|---|---:|---:|---:|---:|---:|---:|
| **`mode=0`（原版基线）** | **66.00 FPS** | 15.07 / 17.71 ms | **1,563 MB/s** | **303 MB/s** | **80.2%** | 4,520 次/帧 |
| **`mode=1`（`20 MiB` 窄档）** | **66.62 FPS** *(+0.95%)* | 14.94 / 17.47 ms | 1,590 MB/s | 296 MB/s | 80.6% | 1,227 次/帧 |
| **`mode=1`（`256 MiB` 宽档）** | **63.44 FPS** *(-3.87%)* | 15.72 / 18.04 ms | 1,630 MB/s | **197 MB/s** | **70.2%** | **0 次/帧** |

**证伪铁证**：
1. 宽档确实将 `164 MiB` 动态缓冲提拔进了 `GPU_UPLOAD`，把普通 `UPLOAD` 根绑定彻底清零，但 **FPS 不升反降（`-3.87%`）**；
2. 原因一清二楚：① 真实游戏的 PCIe 接收流量仅 `~1.66 GB/s`，远未触及 OCuLink Gen4 ×4 的 `6.1 GB/s` 带宽上限；② 游戏那 4,520 次根绑定只读局部小常量（命中 GPU L2 Cache），且引擎自身每帧已在执行 `118 次` `CopyBufferRegion(UPLOAD → DEFAULT)`（`~440 MB/s`）；强行把源缓冲改成显存 `GPU_UPLOAD` 后，CPU 跨桥写 Write-Combining 变慢拖累了渲染线程（GPU SM 利用率从 `80.2%` 掉到 `70.2%`），随后 GPU 又在显存内多做了一次冗余拷贝。

### 3. Phase 4：4K DLSS 性能档微秒级解剖——抓出真正的「跨桥串行气泡」
进一步在 `dxgi.dll v0.3.1` 植入微秒级 API 耗时与分线程 CPU 统计，测试 **《黑神话：悟空》官方完整大场景 Benchmark** 与 **《影之刃零》4K DLSS 性能档（静态 + 山谷开阔视角持续转镜）**：

| 测试场景（4K DLSS 性能档，关 VSync / 关 FG） | 实测 FPS | GPU 利用率 (均/中位) | `RX` / `TX` (MB/s) | 每帧 `ExecuteCommandLists` | 关键线程单核 CPU 活跃度 |
|---|---:|---:|---:|---:|---|
| **《黑神话：悟空》完整 Benchmark** | **官方 74 FPS**<br>*(最高 85 / 最低 27)* | 80.2% / **91.0%** | 908 / **385** | **24.5 次/帧** *(1.06 ms)* | 大场景偶发掉至 49.5 FPS (GPU 50.5%) |
| **《影之刃零》木屋静态（从质量切性能档）** | **69.04 FPS**<br>*(质量档为 66.00)* | **74.6%** / 75.0% | 1,665 / **314** | **89.6 次/帧** *(2.16 ms)* | `Game` 39.6% / `Render` 41.6% / `RHI` 57.1% |
| **《影之刃零》山谷开阔持续转镜** | **65.93 FPS** | **73.7%** *(瞬时 67%)* | 1,658 / **313** | **98.0 次/帧** *(2.31 ms)* | `Game` 39.8% / `Render` 40.8% / `RHI` 57.9% |

**核心物理真相水落石出**：
1. **100% 复现「降分辨率不涨帧、GPU 开始闲置」**：《影之刃零》从 DLSS 质量档切到性能档，渲染像素砍半，GPU 利用率往下掉（Overlay 瞬时 `GPU 67% | CPU 53% | 系统延迟 74.4 ms`），但帧率死死钉在 **`66–69 FPS`（`14.5–15.0 ms`）** 纹丝不动！木屋空山谷已是 `15 ms` 底噪，一旦进入多怪战斗或城镇大场景，这层非像素开销翻倍到 `25–30 ms` 就是 **30–40 FPS + GPU 50% 占用**（若再叠加原配置 `60Hz VSync` 越过 `16.67 ms` 红线，当场触发半刷新率掉档锁 30 帧）。
2. **不是单点带宽打满，而是「高频碎提交 + 高额反向 Readback + 多线程跨桥串行气泡」**：
   - CPU 没有任何一个核跑满 100%（最高的 `RHIThread` 单核仅 `57.9%`，`Game/Render` 仅 `~40%`），GPU 也没跑满，PCIe 带宽也没跑满——**CPU 与 GPU 在跨桥延迟下互相等**；
   - 《影之刃零》每帧竟调用 **`98 次` `ExecuteCommandLists`**（仅提交 API 本身就在 CPU 上吃掉 **`2.31 ms/帧`**），外加每帧 **`~80 次` Fence 事件等待（`RHIInterruptThread` 累计 `13.2 ms/帧`）、`875 次` Fence 轮询**；
   - 两款游戏均存在惊人的 **GPU→Host 反向抽水（`TX` 高达 `313–385 MB/s`）**：包括《黑神话》每帧 `3.34 MB` Buffer Readback + Texture Readback、《影之刃零》每帧近百次分桶读回与 Query Resolve（遮挡剔除 / HZB / Nanite 流送反馈）。
3. **这也彻底解释了「直插 x16 > OCuLink x4 > USB4」的三级体验断崖**：
   - 直插 PCIe x16 延迟亚微秒级、双向带宽充裕，每帧近百次门铃提交与回传被轻松掩盖；
   - OCuLink Gen4 ×4 还能把《黑神话》撑在平均 74 FPS、把《影之刃零》空场景撑在 66 FPS，但大场景战斗就会被串行气泡压到 30–40 FPS；
   - 到了隧道协议封装更深、往返延迟翻倍且双向并发有效带宽仅 `~2.5 GB/s` 的 **USB4 显卡坞**，这套 `1.6 GB/s RX + 0.38 GB/s TX + 百次碎提交/中断` 直接撞墙崩盘！

## 三、灵魂拷问：这问题能在外部用黑盒 DLL 修好吗？

**实话实说：在 D3D12 外部黑盒拦截层（`dxgi.dll`）没法优雅根治，不值得硬写成通用软件！** 账算得非常清楚：

1. **为什么 `UPLOAD → GPU_UPLOAD` 好写但没用，而真正的病灶在外部黑盒不敢乱动？**
   - 改堆类型只是在创建资源时把 `2` 改成 `5`，不碰同步语义；但真游戏证明瓶颈不在那儿。
   - 真病灶之一是 **每帧 98 次 `ExecuteCommandLists` 碎提交**：如果在外部 `dxgi.dll` 强行扣住 CommandList 攒批提交（Batching），由于引擎在两次提交之间往往夹着跨队列（Graphics ↔ AsyncCompute）或 CPU 侧的 `Fence Signal / Wait`，黑盒层不重写全套跨队列依赖图，扣单下一毫秒就会 **GPU 跨队列死锁（Deadlock）**；且就算把 `2.31 ms` 提交开销全省掉，最多也就从 `15 ms (66 FPS)` 变成 `13 ms (76 FPS)`，救不了大场景。
   - 真病灶之二是 **每帧 `310–385 MB/s` 的反向 Readback 与同步反馈（HZB / 遮挡查询 / Nanite 流送页表）**：外部 `dxgi.dll` 看到的只是一块无语义字节流，根本分不清哪块读回可以多延迟 2 帧、哪块读回是本帧逻辑立刻要用的——强塞上一帧旧数据轻则模型闪烁（Pop-in），重则越界闪退。
2. **那玩家手头真正管用的务实解法是什么？**
   - **立竿见影第 1 招：关掉 60Hz 普通垂直同步（`bUseVSync=False`）+ 关掉后台限帧**：避免单帧刚过 `16.67 ms` 就被传统双缓冲 VSync 一脚踹进 `30 FPS` 半刷新率深坑；
   - **立竿见影第 2 招：直接开 DLSS 帧生成（Frame Generation）！** 既然在 OCuLink 上 4K DLSS 性能档时 5090 有 **30%～50% 的算力因为等 CPU/PCIe 气泡在白白睡大觉**，开启帧生成正好直接吃掉这部分闲置的本地 GDDR7 算力，绕过 CPU/PCIe 提交墙把画面帧率翻倍顶上去；
   - **第 3 招（仅限未锁死 `Engine.ini` 的 UE5 游戏）**：在 `Engine.ini` 适当放宽遮挡查询缓冲帧数（如 `r.NumBufferedOcclusionQueries=4`）减少跨桥等结果气泡；至于彻底根治，只能靠下一代 **Thunderbolt 5 / PCIe Gen5 ×4** 硬件提速 + 虚幻引擎官方改掉每帧近百次碎提交的毛病了。

> **方法论小结**：昨晚花 4 小时从反汇编、微基准（快 288 倍！）一路打穿到真机两款 3A 游戏微秒级证伪，最大的价值就是**没有被合成微基准的“288 倍暴涨”骗去闭门造车写两周复杂内存池**——真机跑一圈，行就是行，不行当场看清物理边界收工，爽快！
